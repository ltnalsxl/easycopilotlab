## M0. 오리엔테이션 — 오늘 만들 에이전트 미리보기

**영상 길이:** 약 4분  
**목적:** 오늘 하루의 여정을 미리 보여주고 동기 부여  

---

[화면] 강사 얼굴 + 하단 자막 "M0. 오리엔테이션"

안녕하세요, 여러분. 오늘 하루가 끝나면 여러분의 PC에 **AI 직원이 한 명 생깁니다.** 코드 한 줄 없이요.

[화면] 완성된 에이전트 데모 화면

지금 보시는 화면이 오늘의 결과물입니다. 이 에이전트에게 물어보겠습니다.

"연차 며칠 남았어요?" — 바로 답변이 옵니다.
"경비처리 담당자 누구예요?" — 이름, 연락처, 이메일까지 찾아줍니다.
"담당자한테 직접 문의하고 싶어요" — 이메일까지 자동으로 보내줍니다.

[자막] FAQ 자동 답변 / 담당자 조회 / 복리후생 안내 / 메일 전달 / 대화기록 자동 저장

이게 오늘 만들 에이전트가 하는 일 **다섯 가지**입니다.
FAQ 자동 답변, 담당자 조회, 복리후생 안내, 이메일로 문의 전달, 그리고 모든 대화를 엑셀에 자동 기록.

[화면] 오늘의 로드맵 타임라인 (M0→M17)

오늘 과정은 이렇게 진행됩니다.
오전에는 **원리를 이해**하고, 오후에는 **직접 만듭니다.**
모듈은 총 18개인데, 하나하나가 벽돌 쌓듯이 연결됩니다.

처음엔 빈 에이전트에서 시작해서, 지침을 주고, 지식을 주고, 도구를 연결하면…
오후가 끝날 때쯤엔 지금 보신 것처럼 **진짜 일하는 AI 직원**이 완성됩니다.

[화면] 강사 얼굴

"이거 진짜 코딩 없이 되나요?"라고 생각하실 수 있는데요.
네, 됩니다. 오늘 직접 경험하시게 될 겁니다.

자, 그럼 첫 번째 모듈로 넘어가겠습니다. 먼저 **Copilot이 실제로 어떻게 동작하는지**, 그 원리부터 살펴보겠습니다.

## M1. 코파일럿 동작원리 — 당신은 AI와 대화하고 있지 않다

**영상 길이:** 약 5분  
**목적:** 오케스트레이터 개념을 이해시켜, 이후 에이전트 설계의 기반 마련  

---

[화면] 강사 얼굴 + 하단 자막 "M1. 코파일럿 동작원리"

여러분, ChatGPT에 질문하면 AI가 직접 대답한다고 생각하시죠?
**아닙니다.**

[화면] 오케스트레이터 구조도 애니메이션
[자막] 사용자 → 오케스트레이터 → LLM

여러분과 AI 사이에는 보이지 않는 **중개자**가 있습니다. 이걸 **오케스트레이터**라고 부릅니다.

비유를 하나 들어볼게요.  
여러분이 콜센터에 전화했다고 해봅시다.
전화를 받는 건 **상담원**이에요. AI가 아닙니다.
상담원이 여러분 말을 듣고, 필요하면 서류를 찾아보고, 다른 부서에 전화하고, 시스템을 조회해서 답을 만들어 줍니다.

[자막] 오케스트레이터 = 상담원 / LLM = 전문가

이게 오케스트레이터의 역할입니다. 오케스트레이터가 하는 일은 **세 가지**입니다.

[화면] 세 가지 역할 목록

**첫째, 성격을 부여합니다.**
오케스트레이터는 AI에게 질문을 넘기기 전에, 이런 지시를 먼저 넣습니다.
"너는 HR 전문 도우미야. 사내 규정만 답해. 정치 이야기는 하지 마."
이게 **시스템 프롬프트**입니다.

같은 GPT 모델이라도, 시스템 프롬프트가 다르면 완전히 다른 AI처럼 동작합니다.
ChatGPT는 "만능 비서"이고, Copilot은 "업무 도우미"이고, 우리가 만들 에이전트는 "HR 전문가"입니다.
**모델은 같고, 시스템 프롬프트가 다를 뿐입니다.**

[자막] 같은 엔진, 다른 시스템 프롬프트 = 다른 AI

**둘째, 수단을 동원합니다.**
"오늘 환율 알려줘"라고 하면, AI가 인터넷을 검색하는 것처럼 보이지만
실은 오케스트레이터가 Bing 검색 도구를 호출해서 결과를 가져온 다음, AI에게 넘기는 겁니다.
파일 읽기, 코드 실행, 이미지 생성, 이메일 검색 — 이 모든 건 오케스트레이터의 **도구 호출**입니다.

**셋째, 맥락을 관리합니다.**
"아까 그 파일" 이라고만 해도 이해하는 건, 오케스트레이터가 이전 대화를 기억하고 있기 때문입니다.

[화면] 강사 얼굴

자, 이게 왜 중요할까요?

오늘 오후에 여러분이 작성할 **지침**이 바로 이 시스템 프롬프트입니다.
여러분이 연결할 **지식과 도구**가 바로 오케스트레이터가 사용할 수단입니다.

즉, **에이전트를 만든다는 것은 오케스트레이터를 설정하는 것**입니다.
이 구조를 알고 있으면, 앞으로의 모든 실습이 훨씬 쉽게 이해됩니다.

## M2. 에이전트 활용 — 몰입형 vs 인컨텍스트

**영상 길이:** 약 5분  
**목적:** 에이전트의 두 가지 사용 방식을 이해하고 실무 적용 판단  

---

[화면] 강사 얼굴 + 하단 자막 "M2. 에이전트 활용 방식"

에이전트를 만들면, 사용하는 방법이 **두 가지**입니다.
하나는 **몰입형**, 하나는 **인컨텍스트**입니다.

[화면] 몰입형 vs 인컨텍스트 비교 이미지

비유를 들어볼게요.

**몰입형**은 **전용 창구**입니다.
은행에서 번호표 뽑고, 전용 창구에 앉아서 상담받는 거예요.
에이전트에게 집중해서 여러 질문을 연속으로 합니다.
Copilot에서 에이전트 이름을 클릭하면, 에이전트 전용 화면이 열립니다.

[화면] 몰입형 데모 스크린샷

신입사원 온보딩처럼 물어볼 게 많을 때, 깊이 있는 대화가 필요할 때 적합합니다.

[화면] 인컨텍스트 데모 스크린샷

**인컨텍스트**는 **옆자리 동료**입니다.
업무하다가 옆자리 동료한테 "야, 복지포인트 어디서 써?" 하고 물어보는 거예요.
Copilot 채팅창에서 `@HR도우미`라고 치면 됩니다.

[자막] @에이전트이름 + 질문 = 인컨텍스트 호출

인컨텍스트의 **진짜 힘**은 여기에 있습니다.
**하나의 대화에서 여러 에이전트를 번갈아 부를 수 있다**는 겁니다.

[화면] 실전 워크플로 — 여러 에이전트 조합 다이어그램

예를 들어, 내일 A사 미팅을 준비한다고 해봅시다.
먼저 `@영업지원` 에이전트에게 A사 영업 히스토리를 물어보고,
그 다음 `@리서치` 도구로 산업 트렌드를 검색하고,
마지막에 Copilot에게 "지금까지 내용 종합해서 브리핑 정리해줘"라고 하면
**하나의 대화에서 미팅 준비가 끝납니다.**

[화면] 강사 얼굴

정리하면,
깊은 대화가 필요하면 **몰입형**, 빠르게 물어볼 거면 **인컨텍스트**.
하나의 에이전트로 **두 가지 방식 모두 사용 가능**합니다.

오늘 오후 M10에서 직접 게시한 다음, 두 방식 모두 테스트해 봅니다.

## M3. 에이전트 만들기 시작 — 첫 번째 에이전트 만들기

**영상 길이:** 약 5분  
**목적:** 에이전트 빌더와 Copilot Studio의 차이를 이해하고, 실습 흐름 안내  

---

[화면] 강사 얼굴 + 하단 자막 "M3. 에이전트 만들기 시작"

자, 이제부터 직접 만듭니다.

에이전트를 만드는 도구는 **두 가지**입니다.
하나는 **에이전트 빌더**, 하나는 **Copilot Studio**입니다.

[화면] 에이전트 빌더 UI 스크린샷

**에이전트 빌더**는 M365 Copilot 안에 내장된 간편 도구입니다.
30초면 에이전트를 만들 수 있습니다.
"Copilot Studio 라이트 버전"이라고 생각하시면 됩니다.

그런데 이 에이전트 빌더, 생각보다 **강력합니다.**
지식 연결, 이미지 생성, 코드 실행, 데이터 분석까지 기본 내장되어 있어요.
많은 경우에 에이전트 빌더만으로 충분합니다.

[화면] 에이전트 빌더 vs Copilot Studio 비교표
[자막] 에이전트 빌더 = 기본 | Copilot Studio = 확장

그런데 왜 Copilot Studio도 배울까요?

**에이전트 빌더에 없는 것들이 있기 때문입니다.**
토픽, 커넥터, Power Automate 연동, AI 프롬프트, 멀티에이전트, MCP, 트리거 — 
이런 확장 기능은 **Copilot Studio에서만** 가능합니다.

비유하자면, 에이전트 빌더는 **기본 제공 엔진**, Copilot Studio는 **엔진 + 추가 부품**입니다.

[화면] 실습 흐름 안내

오늘 실습은 이렇게 진행됩니다.

**실습 ①** 에이전트 빌더에서 HR 도우미 에이전트를 만듭니다.
**실습 ②** 만든 에이전트를 Copilot Studio로 가져옵니다.
**실습 ③** Copilot Studio에서 한국어 에이전트를 새로 만듭니다.

여기서 중요한 포인트가 하나 있어요.

[자막] ⚠️ 에이전트 빌더에서 만든 에이전트 = 영어 고정

에이전트 빌더에서 만든 에이전트를 Studio로 가져오면 **언어가 영어로 고정**됩니다.
한국어 에이전트를 만들려면 **Studio에서 새로 만들어야** 합니다.
그래서 실습 ③이 꼭 필요합니다.

[화면] 강사 얼굴

자, 그럼 실습으로 들어가겠습니다. 화면을 따라 해주세요.

## M3a. 부록 — 샘플 에이전트 체험

**영상 길이:** 약 4분  
**목적:** 지침 하나로 에이전트의 성격이 완전히 달라진다는 체험  

---

[화면] 강사 얼굴 + 하단 자막 "M3a. 샘플 에이전트 체험"

본격적인 실습에 들어가기 전에, **지침의 힘**을 먼저 체험해봅시다.

지금부터 보여드릴 건 **똑같은 에이전트 빌더**에 **다른 지침**을 넣었을 때 어떤 일이 일어나는지입니다.

[화면] 6가지 샘플 에이전트 목록

준비한 샘플은 여섯 가지입니다.

**A. 롤플레이 트레이너** — 고객, 파트너, 상사 역할을 시뮬레이션해서 대화 연습을 시켜줍니다. 5~7번 대화 후에 점수까지 매겨줘요.

**B. 글쓰기 스타일 에디터** — 같은 내용을 비즈니스 이메일, 팀즈 메시지, 공식 보고서, 한 줄 요약 네 가지 스타일로 변환합니다.

**C. 전문가 패널 토론** — 전략가, 위기관리자, 실무자, 혁신가 네 명의 관점에서 하나의 주제를 토론합니다.

[자막] 지침만 바꿔도 완전히 다른 에이전트

**D. 회의록 자동 정리** — 뒤죽박죽 메모를 넣으면 요약, 핵심 논의, 결정사항, 후속 할 일까지 정리해줍니다.

**E. 이메일 초안 생성** — 상황을 설명하면 격식체, 편한 말투, 초간결 버전 세 가지를 만들어줍니다.

**F. 면접 질문 생성기** — 직무 기술서를 넣으면 역량 질문 3개, 상황 질문 2개, 조직문화 1개, 성장잠재력 1개를 만들어줍니다.

[화면] 실제 샘플 에이전트 대화 시연

이 여섯 개가 전부 **지침만 다를 뿐**, 모델도, 지식도, 도구도 같습니다.
복사-붙여넣기 한 번이면 바로 사용할 수 있는 지침 예시를 교재에 넣어드렸으니, 직접 해보세요.

[화면] 강사 얼굴

핵심은 이겁니다.
**잘 쓴 지침 하나가 에이전트의 성격을 완전히 바꿉니다.**
역할, 범위, 태도, 출력 형식 — 이 네 가지를 명확히 적으면 됩니다.
이 원리를 M6에서 본격적으로 다룹니다.

## M4. 에이전트의 4가지 구성요소

**영상 길이:** 약 5분  
**목적:** 에이전트의 4대 구성요소 프레임워크를 설명하고, 이후 모듈 구조 안내  

---

[화면] 강사 얼굴 + 하단 자막 "M4. 에이전트의 구성요소"

에이전트를 분해하면 **네 가지** 부품으로 나뉩니다.
오늘 오후의 모든 실습이 이 네 가지 중 하나를 다룹니다.

[화면] 4대 구성요소 다이어그램 애니메이션
[자막] 오케스트레이터 / 지침 / 지식 / 도구

**첫째, 오케스트레이터.**
자동차로 치면 **엔진**입니다.
어떤 AI 모델을 쓸지 결정하고, 사용자의 질문을 분석해서 어떤 도구를 쓸지 판단하고, 최종 답변을 생성합니다.

**둘째, 지침.**
**신입사원의 업무 매뉴얼**입니다.
"넌 HR 전문가야. 존댓말 써. 모르는 건 모른다고 해." — 이런 내용을 적습니다.

**셋째, 지식.**
**교과서**입니다.
에이전트가 답변할 때 참고하는 문서들이에요. 사내 규정, FAQ, 담당자 목록 같은 파일을 업로드합니다.

**넷째, 도구.**
에이전트의 **손과 발**입니다.
토픽, 커넥터, Power Automate 흐름, AI 프롬프트, 멀티에이전트, MCP, 트리거 — 이 모든 것이 도구입니다.

[화면] 모듈 매핑 표

이 네 가지가 앞으로의 모듈과 어떻게 연결되는지 보여드릴게요.

| 구성요소 | 해당 모듈 |
|---------|----------|
| 오케스트레이터 | M5 |
| 지침 | M6 |
| 지식 | M7 |
| 도구 | M8~M16 전부 |

[자막] 도구 = M8부터 M16까지의 모든 모듈

보시다시피 **도구가 가장 많은 비중을 차지합니다.**
토픽, 커넥터, Flow, AI 프롬프트, 멀티에이전트, MCP, 트리거 — 
이것들이 전부 도구의 하위 항목입니다.

[화면] Copilot Studio UI 네비게이션

Copilot Studio를 열면 이 네 가지가 어디 있는지 확인할 수 있습니다.
왼쪽 메뉴에서 개요, 지침, 지식, 토픽, 작업, 설정이 보이죠.
설정 안에 오케스트레이터 관련 옵션이 있습니다.

[화면] 강사 얼굴

지금은 "아, 네 가지가 있구나" 정도만 기억하시면 됩니다.
다음 모듈부터 하나씩 실습하면서 자연스럽게 체득하게 됩니다.

Copilot Studio에서 **생성형 AI 오케스트레이션이 켜져 있는지** 꼭 확인하세요.

## M5. 1요소 오케스트레이터 — 모델 변경 + 설정 실습

**영상 길이:** 약 5분  
**목적:** AI 모델 선택의 의미를 이해하고, 설정 변경의 영향 파악  

---

[화면] 강사 얼굴 + 하단 자막 "M5. 오케스트레이터 — AI 모델 설정"

네 가지 구성요소 중 첫 번째, **오케스트레이터**입니다.

오케스트레이터는 에이전트의 **엔진**이라고 했죠.
이 엔진의 핵심이 바로 **어떤 AI 모델을 선택하느냐**입니다.

[화면] 모델 비교표
[자막] OpenAI 계열 + Anthropic 계열

현재 Copilot Studio에서 선택할 수 있는 모델은 크게 두 계열입니다.

**OpenAI 계열:**
- GPT-4.1 — 기본값입니다. 빠르고 분석에 강합니다.
- GPT-5 Chat — 대화에 최적화된 모델
- GPT-5 Auto — 자동으로 판단 깊이를 조절하는 프리뷰 버전
- GPT-5 Reasoning — 가장 깊이 생각하는 추론 특화 모델

**Anthropic 계열:**
- Claude Sonnet 4.5 — 범용 + 콘텐츠 생성에 강함
- Claude Sonnet 4.6 — 빠르고 균형 잡힌 모델
- Claude Opus 4.6 — 가장 깊은 추론을 하는 모델

[자막] 모델이 다르면 → 답변 깊이, 속도, 비용이 다르다

어떤 모델을 고르느냐에 따라 **답변의 깊이, 속도, 비용**이 달라집니다.

간단한 FAQ 에이전트라면 GPT-4.1으로 충분하고,
복잡한 분석이나 긴 문서 처리가 필요하면 Reasoning이나 Opus 계열을 고려합니다.

[화면] 실습 화면 — 모델 변경 전/후 비교

이번 실습에서는 같은 질문을 **서로 다른 모델**에게 던져봅니다.
답변의 차이를 직접 눈으로 확인하는 거예요.

그리고 **에이전트 설정**도 조정해봅니다.
응답 길이, 언어, 안전 수준 — 이런 설정 항목들이 어디에 있고, 바꾸면 어떤 차이가 나는지 확인합니다.

[화면] 강사 얼굴

지금 단계에서 모델별 차이를 완벽히 이해할 필요는 없습니다.
**"여기서 모델을 바꿀 수 있고, 바꾸면 영향이 있다"** — 이것만 기억하세요.
실습하면서 자연스럽게 감이 옵니다.

## M6. 2요소 지침 — 좋은 지침 쓰기

**영상 길이:** 약 5분  
**목적:** 좋은 지침의 4가지 요소와 6가지 원칙 설명  

---

[화면] 강사 얼굴 + 하단 자막 "M6. 지침 — 에이전트의 업무 매뉴얼"

두 번째 구성요소, **지침**입니다.
신입사원에게 업무 매뉴얼을 잘 써주면 일을 잘 하듯이, **에이전트도 지침이 좋아야 잘 동작합니다.**

[화면] 지침의 4가지 필수 요소

좋은 지침에는 **네 가지가 반드시** 들어가야 합니다.

[자막] ① 역할 ② 범위 ③ 태도 ④ 원칙

**① 역할** — "넌 누구냐?"
"당신은 ○○회사의 HR 전문 도우미입니다" 처럼, **소속과 역할을 구체적으로** 적습니다.
"친절한 AI"가 아니라, "○○기업 인사팀의 복리후생 전문 상담원"입니다.

**② 범위** — "뭘 다루냐?"
"연차, 경비처리, 복지포인트에 대해서만 답하세요."
이때 **"다루는 것"만 나열**합니다. "정치 이야기 하지 마" 같은 제외 목록이 아니라, 포함 목록을 적으세요.

**③ 태도** — "어떻게 말하냐?"
"친절하게" 같은 추상적 표현 대신, **행동 지시**를 합니다.
"존댓말을 사용하세요." "핵심 내용을 먼저 말하세요." "200자 이내로 답하세요."

**④ 원칙** — "반드시 지켜야 할 것은?"
여기서 **가장 중요한 원칙**이 있습니다.

[화면] 경고 강조 화면
[자막] ⚠️ "모르면 어떻게 할지" 반드시 정의하세요

**"모르는 건 모른다고 답하세요. 절대 추측하지 마세요."**

이 한 줄을 빼면 에이전트가 **지어냅니다.** 이걸 할루시네이션이라고 하죠.
사내 규정을 잘못 답하면 실질적인 문제가 됩니다.

[화면] 6가지 골든 룰 목록

정리하면 **6가지 골든 룰**입니다.
1. 역할은 소속까지 구체적으로
2. 범위는 포함 목록으로
3. 태도는 행동 지시로
4. "모를 때의 대응"을 반드시 정의
5. 언어와 형식을 지정 (한국어, 200자 이내 등)
6. 짧게 써라 — 200~500자가 최적

[화면] 강사 얼굴

지침 작성은 **코딩이 아니라 글쓰기**입니다.
문과적 역량이 빛나는 영역이에요.
실습에서 직접 지침을 작성한 후, 같은 질문의 답변이 어떻게 달라지는지 비교해봅니다.

## M7. 3요소 지식 — RAG 개념 + 참조문서 업로드

**영상 길이:** 약 5분  
**목적:** 지식 원리(RAG)를 쉽게 설명하고, 문서 구조의 중요성 인식  

---

[화면] 강사 얼굴 + 하단 자막 "M7. 지식 — 에이전트의 교과서"

세 번째 구성요소, **지식**입니다.

[자막] 지식 = 에이전트의 교과서

에이전트가 답변할 때 참고하는 문서, 이게 **지식**입니다.
교과서 없이 시험 보면 답을 지어내듯이, 지식 없는 에이전트도 **지어냅니다.**

[화면] 지식 연결 전/후 답변 비교 애니메이션

같은 질문을 던져볼게요. "경조사 지원금이 얼마예요?"
지식 연결 전 — 에이전트가 "일반적으로 10~30만원 수준입니다" 라고 추측합니다.
지식 연결 후 — "당사 규정에 따르면 결혼 축의금 20만원, 조의금 10만원입니다" 라고 **출처와 함께** 정확히 답합니다.

[화면] 4가지 지식 연결 방법 표

지식을 연결하는 방법은 **네 가지**입니다.

| 방법 | 난이도 | 특징 |
|-----|-------|------|
| 파일 업로드 | ⭐ | 가장 쉬움, 수동 업데이트 |
| 웹 URL | ⭐⭐ | 주기적 동기화 |
| SharePoint | ⭐⭐⭐ | 자동 업데이트, 권한 제어 |
| Dataverse | ⭐⭐⭐ | 실시간, 권한 제어 |

오늘은 **파일 업로드**로 시작합니다. 가장 빠르고 확실한 방법이에요.
실제 운영할 때는 SharePoint로 옮기면 자동으로 최신 문서가 반영됩니다.

[화면] 좋은 문서 vs 나쁜 문서 비교

여기서 핵심 팁 하나.
**문서의 구조가 답변 품질을 결정합니다.**

장문의 서술형 문서보다, **Q&A 형식 + 표 + 명확한 제목** 구조가 훨씬 좋습니다.
AI가 정보를 찾아서 추출하기 쉽기 때문이에요.

[자막] 구조화된 문서 > 서술형 문서

예를 들면:
❌ "당사의 연차 제도는 근속년수에 따라 차등 지급되며..."
⭕ "Q: 연차는 몇 일인가요? A: 1년 미만 11일, 1~3년 15일, 3년 이상 20일"

[화면] 강사 얼굴

실습에서 준비된 5개 문서를 업로드한 다음, 같은 질문을 던져서 답변 품질이 어떻게 올라가는지 직접 확인합니다.

## M8. 4요소 도구들 — 도구가 채택되는 원리

**영상 길이:** 약 4분  
**목적:** 도구 채택 메커니즘을 이해하고, 이후 M9~M16의 맥락 파악  

---

[화면] 강사 얼굴 + 하단 자막 "M8. 도구 — 에이전트의 손과 발"

네 번째 구성요소, **도구**입니다.
에이전트의 **손과 발**이라고 했죠.

[화면] 도구 목록 아이콘 나열
[자막] 토픽 / 커넥터 / Flow / AI 프롬프트 / 멀티에이전트 / MCP / 트리거

토픽, 커넥터, Power Automate 흐름, AI 프롬프트, 멀티에이전트, MCP, 트리거 — 
오케스트레이터·지침·지식을 제외한 **나머지 전부가 도구**입니다.

그런데 중요한 질문이 있어요.
에이전트는 **어떻게 적절한 도구를 골라서 사용할까요?**

[화면] 도구 채택 플로차트 애니메이션

사용자가 질문을 하면, **오케스트레이터가 판단**합니다.
"이 질문에는 어떤 도구가 필요하지?"
그리고 가장 적합한 도구를 선택해서 실행합니다.

이때 오케스트레이터가 판단하는 기준은 **두 가지**입니다.

[자막] ① 도구의 설명(Description) ② 지침의 명시적 규칙

**첫째, 도구의 설명문.**
각 도구에는 "이 도구는 ~할 때 사용합니다"라는 설명이 있습니다.
이 설명이 **구체적이고 명확**해야 오케스트레이터가 제대로 선택합니다.
설명이 모호하면? 오케스트레이터가 그 도구를 **무시합니다.**

**둘째, 지침의 명시적 규칙.**
지침에 "사용자가 ~라고 하면 반드시 ○○ 도구를 사용하세요"라고 적으면,
오케스트레이터가 이 규칙을 따릅니다. 이걸 나중에 **STRICT RULES**라고 부릅니다.

[화면] 강사 얼굴

이 원리만 알면 됩니다.
**도구를 만드는 것만큼, 도구의 설명을 잘 쓰는 게 중요하다.**

다음 모듈 M9부터 M16까지, 도구를 하나씩 만들어 연결합니다.
도구가 연결되는 순간, 에이전트는 채팅봇에서 **진짜 일하는 AI 직원**으로 변합니다.

## M9. 도구 — 토픽과 변수

**영상 길이:** 약 5분  
**목적:** 토픽과 변수의 개념, 오케스트레이터와의 역할 분담 이해  

---

[화면] 강사 얼굴 + 하단 자막 "M9. 토픽과 변수"

첫 번째 도구, **토픽**입니다.

[자막] 토픽 = 대본 · 시나리오

토픽은 **대본**입니다.
특정 상황이 오면 이 대본대로 진행하라는 **미리 짜둔 시나리오**예요.

예를 들어, 사용자가 "담당자 알려줘"라고 하면
오케스트레이터가 판단합니다. "아, 이건 담당자 조회 대본이 있지."
그러면 그 토픽 — 즉, 그 대본을 실행합니다.

[화면] 토픽 실행 흐름 다이어그램

그리고 토픽이 실행되면서 정보를 모으는데, 이 정보를 저장하는 게 **변수**입니다.

[자막] 변수 = 포스트잇 메모

변수는 **포스트잇**이에요.
토픽이 대화하면서 중요한 정보를 포스트잇에 적어두는 거예요.
"담당자 이름: 김철수, 연락처: 1234" — 이런 걸 적어두면
나중에 다른 토픽이나 Flow에서도 이 포스트잇을 꺼내볼 수 있습니다.

[화면] 글로벌 변수 vs 로컬 변수 비교

변수에는 **글로벌**과 **로컬** 두 종류가 있는데, 오늘은 **글로벌만** 사용합니다.
글로벌 변수는 가슴에 붙인 포스트잇 — 어디서든 볼 수 있습니다.
로컬 변수는 그 대본 안에서만 보이는 포스트잇입니다.

[화면] 핵심 아키텍처 설명

여기서 설계의 핵심을 말씀드릴게요.

**토픽은 정보를 모으는 역할, 오케스트레이터가 말하는 역할.**

토픽이 담당자 이름과 연락처를 변수에 저장하면,
오케스트레이터가 그 변수를 읽어서 자연스러운 문장으로 답변합니다.

왜 이렇게 분리할까요?
토픽이 직접 답변을 만들면 **딱딱한 스크립트**가 됩니다.
오케스트레이터가 답하면 **자연스러운 AI 대화**가 됩니다.

[자막] 토픽 = 데이터 수집 / 오케스트레이터 = 답변 생성

[화면] 실습 안내

이번 실습에서는 세 가지를 만듭니다.
**실습 ①** HRdoc 토픽 — 사내 규정 관련 질문 처리
**실습 ②** Contact 토픽 — 담당자 검색
**실습 ③** STRICT RULES — 지침에 명시적 도구 호출 규칙 추가

[화면] 강사 얼굴

STRICT RULES를 추가하면 "담당자 알려줘"라고 할 때 **반드시** Contact 토픽이 실행됩니다.
이건 M8에서 설명한 **도구 채택의 두 번째 방법**이었죠.

---

## M10. 게시와 공유 — 에이전트 배포

**영상 길이:** 약 5분  
**목적:** 게시/채널/공유의 차이를 명확히 하고, 배포 절차 안내  

---

[화면] 강사 얼굴 + 하단 자막 "M10. 게시와 공유"

에이전트를 만들었으면 이제 **세상에 내보내야** 합니다.

[화면] 용어 정리 표
[자막] 게시 ≠ 채널 ≠ 공유

먼저 용어를 정리합니다. 이 세 가지가 자주 헷갈립니다.

**게시(Publish)** — 최신 변경사항을 반영하는 **배포 버튼**입니다.
앱스토어에 앱을 업로드하는 것과 같아요.
지침을 바꾸거나, 지식을 추가하거나, 토픽을 만들 때마다 **게시를 눌러야** 반영됩니다.

**채널(Channel)** — 에이전트가 어디에 나타나는지, **설치 장소**입니다.
M365 Copilot, Teams, 웹사이트 — 이 중 어디에 노출할지 선택합니다.
채널은 **한 번만 설정**하면 되고, 이후에는 게시만 누르면 자동 반영됩니다.

**공유(Share)** — 누가 이 에이전트를 쓸 수 있는지, **권한 설정**입니다.

[화면] 게시 vs 채널 비유

비유하자면,
게시 = 앱 **업데이트** (빈번)
채널 = 앱 **스토어 등록** (한 번)
공유 = **다운로드 권한** 부여

[화면] 4가지 배포 채널 아이콘

오늘 사용할 채널은 네 가지입니다.

1. **M365 Copilot 몰입형** — 에이전트 전용 화면
2. **M365 Copilot @멘션** — 채팅 중 호출
3. **Teams** — 팀즈 내 사용
4. **웹 임베드** — 외부 웹사이트 노출

[화면] 실습 흐름

실습에서는 세 가지를 합니다.
**실습 ①** 게시 + 채널 활성화
**실습 ②** 몰입형으로 테스트
**실습 ③** @멘션으로 테스트

[화면] 강사 얼굴

이후 M11부터 M16까지 기능을 하나씩 추가할 때마다 **다시 게시** 버튼을 눌러야 합니다.
게시를 안 누르면 테스트 패널에서는 되는데, 실제 채널에서는 안 됩니다.
이거 자주 잊으시니까 꼭 기억해주세요.

게시 후 1~3분 정도 기다렸다가 새로고침하면 반영됩니다.

## M11. 도구 — 커넥터 (대화 자동 기록)

**영상 길이:** 약 5분  
**목적:** 커넥터의 개념과 대화 로깅의 실무 가치 설명  

---

[화면] 강사 얼굴 + 하단 자막 "M11. 커넥터 — 대화 자동 기록"

이번 모듈부터 본격적으로 **도구를 연결**합니다.
첫 번째는 **커넥터**입니다.

[자막] 커넥터 = M365 앱과의 직통 연결

커넥터는 Excel, Outlook, Teams, SharePoint 같은 **M365 앱과 직접 연결하는 파이프**입니다.
하나의 앱에서 **하나의 동작**을 실행합니다. 단순하고 빠릅니다.

이번 실습에서 만들 건 **대화 자동 기록**입니다.

[화면] 대화 자동 기록 흐름도

에이전트가 답변할 때마다, **자동으로 엑셀에 기록**됩니다.
시간, 사용자, 질문 내용, 답변 내용 — 이 네 가지가 한 줄씩 쌓입니다.
사용자는 전혀 몰라요. 백그라운드에서 조용히 기록됩니다.

[자막] 누가 / 언제 / 뭘 물어봤는지 / 뭐라고 답했는지 → 자동 기록

이걸 위해 사용하는 게 **Record 토픽**이라는 특별한 토픽입니다.
일반 토픽은 사용자의 특정 질문에 반응하지만,
Record 토픽은 **오케스트레이터가 답변을 생성할 때마다** 자동으로 실행됩니다.

[화면] 기록 데이터 활용 사례

이 기록이 쌓이면 세 가지에 활용할 수 있습니다.

**첫째, 에이전트 개선.**
가장 많이 묻는 질문 TOP 10을 분석해서, 지식 문서를 보강합니다.

**둘째, 감사와 컴플라이언스.**
누가, 언제, 무슨 질문을 했는지 투명하게 확인할 수 있습니다.

**셋째, 업무 분석.**
질문 패턴을 보면  실제로 어떤 정보가 필요한지 알 수 있습니다.

[화면] 강사 얼굴

실습에서는 먼저 엑셀 파일을 **테이블 형식**으로 준비하고,
Record 토픽에 Excel "행 추가" 커넥터를 연결합니다.

참고로, 커넥터는 **단일 동작**입니다.
여러 단계가 필요한 자동화는 다음 모듈 M12의 **에이전트 흐름(Flow)**에서 다룹니다.

## M12. 도구 — 에이전트 흐름 (Power Automate)

**영상 길이:** 약 5분  
**목적:** 에이전트 흐름의 개념과 커넥터와의 차이를 설명  

---

[화면] 강사 얼굴 + 하단 자막 "M12. 에이전트 흐름 — 다단계 자동화"

M11에서 커넥터를 배웠습니다. **하나의 앱, 하나의 동작.**
이번에는 **여러 단계를 연결하는 흐름**, 에이전트 흐름입니다.

[자막] 커넥터 = 단일 동작 / 에이전트 흐름 = 다단계 자동화

비유하면,
커넥터는 **전화 한 통** 거는 것이고,
에이전트 흐름은 **업무 프로세스 전체**를 자동화하는 것입니다.

[화면] 실습 시나리오 흐름도

오늘 만들 시나리오를 보여드릴게요.
사용자가 "담당자한테 참고해달라고 전해줘"라고 합니다.

이때 이런 일이 자동으로 일어납니다.

**① 오케스트레이터가 STRICT RULES를 확인합니다.**
"문의 전달 요청이면 flow_HRRequest를 실행하라" — 이 규칙을 따릅니다.

**② 흐름이 시작됩니다.**
글로벌 변수에서 문의 맥락을 수집합니다.

**③ AI 프롬프트가 이메일 본문을 생성합니다.**
사용자의 문의 내용을 자연스러운 이메일 문장으로 바꿔줍니다.

**④ 이메일을 발송합니다.**
HR 담당자에게 정리된 이메일이 갑니다.

**⑤ 사용자에게 완료 메시지를 돌려줍니다.**

[자막] 사용자 요청 → STRICT RULES → Flow 실행 → AI 생성 → 이메일 발송 → 완료

[화면] 커넥터 vs 흐름 비교 표

정리하면,
커넥터: Excel에 한 줄 기록 (단일 동작)
흐름: 문의 수집 → AI 작성 → 이메일 발송 (다단계 자동화)

[화면] 강사 얼굴

이번 실습은 두 파트입니다.
**실습 ①** Power Automate에서 직접 흐름을 만듭니다.
**실습 ②** 만든 흐름을 에이전트에 도구로 연결하고, STRICT RULES로 호출 조건을 지정합니다.

흐름 안에서 AI 프롬프트를 쓰는 부분이 나오는데, 이건 다음 모듈 M13에서 더 자세히 설명합니다.

## M13. 고급도구 — AI 프롬프트

**영상 길이:** 약 4분  
**목적:** AI 프롬프트의 4가지 유형과 활용 가능성 소개  

---

[화면] 강사 얼굴 + 하단 자막 "M13. AI 프롬프트"

방금 M12에서 흐름 안에 AI 프롬프트를 넣었죠.
이런 식으로 **자동화 흐름 안에 AI를 끼워 넣는 것**, 이게 AI 프롬프트의 핵심입니다.

[자막] AI 프롬프트 = 자동화 + AI 판단의 결합

기존 자동화는 **규칙 기반**이었습니다.
"A 조건이면 B 실행" — 정해진 순서대로만 움직입니다.

AI 프롬프트를 넣으면 **흐름 중간에 AI가 판단**할 수 있습니다.
분류하고, 요약하고, 생성하고, 분석하는 단계를 넣을 수 있어요.

[화면] 4가지 AI 프롬프트 유형

유형은 **네 가지**입니다.

[자막] 텍스트 / 멀티모달 / 코드 인터프리터 / Word 출력

**① 텍스트** — 가장 기본입니다.
문장을 생성하거나, 분류하거나, 요약합니다.
M12에서 이메일 본문을 자동 생성할 때 사용한 게 이 유형입니다.

**② 멀티모달** — 이미지나 문서를 인식합니다.
영수증 사진을 넣으면 금액, 날짜, 상호를 추출합니다.

**③ 코드 인터프리터** — AI가 코드를 작성하고 실행합니다.
PDF 10개를 처리해서 엑셀 정산표를 만드는 식입니다.

**④ Word 출력** — Word 문서를 자동 생성합니다.
회의록을 넣으면 서식이 갖춰진 보고서가 나옵니다.

[화면] 강사 얼굴

핵심은 이겁니다.
**프롬프트 텍스트만 바꾸면 AI의 행동이 바뀝니다.** 코드 수정이 필요 없어요.

오늘은 텍스트 유형을 실습했고, 나머지 유형은 필요에 따라 확장하시면 됩니다.
Copilot Studio 라이선스에 포함되어 있으니 추가 비용도 없습니다.

---

## M14. 고급도구 — 멀티에이전트

**영상 길이:** 약 5분  
**목적:** 멀티에이전트 아키텍처의 개념과 라우팅 원리 설명  

---

[화면] 강사 얼굴 + 하단 자막 "M14. 멀티에이전트"

지금까지 에이전트 하나를 열심히 만들었습니다.
이번에는 **에이전트가 다른 에이전트를 부르는** 구조를 만듭니다.

[자막] 멀티에이전트 = 에이전트가 에이전트를 호출

[화면] 멀티에이전트 아키텍처 다이어그램

구조는 이렇습니다.

사용자가 질문하면, 먼저 **슈퍼 호스트** 에이전트가 받습니다.
슈퍼 호스트는 **안내데스크**입니다. 직접 일하지 않고, 적합한 전문가에게 연결해줍니다.

"복지포인트 어디서 써요?" → **HR 도우미** 에이전트로 연결
"계약서 검토 부탁해요" → **법무 에이전트**로 연결

[자막] 슈퍼 호스트 = 안내데스크 / 전문가 에이전트 = 각 부서

이게 왜 좋을까요?

**첫째, 전문성.**
하나의 에이전트에 모든 걸 넣으면 지침이 길어지고 혼란스러워집니다.
영역별로 나누면 각 에이전트가 **자기 분야에만 집중**합니다.

**둘째, 확장성.**
새로운 영역이 필요하면 전문가 에이전트를 하나 더 만들어서 슈퍼 호스트에 연결하면 됩니다.
기존 에이전트를 건드릴 필요가 없어요.

**셋째, 재사용.**
HR 도우미는 슈퍼 호스트 말고도 다른 곳에서 단독으로 쓸 수 있습니다.

[화면] 라우팅 메커니즘 설명

슈퍼 호스트가 어떤 에이전트에게 보낼지 어떻게 판단할까요?
**각 에이전트의 설명(Description)**을 보고 판단합니다.

HR 도우미의 설명이 "연차, 복리후생, 경비처리 질문 전담" 이라면,
법무 에이전트의 설명이 "계약서, 사내규정, 법률 자문 전담" 이라면,
슈퍼 호스트는 질문 내용을 보고 **더 관련 있는 쪽으로 라우팅**합니다.

[자막] 라우팅 정확도 = 에이전트 Description의 구체성

그래서 **에이전트의 설명을 구체적으로 쓰는 게 핵심**입니다.
M8에서 "도구의 설명이 중요하다"고 했던 것과 같은 원리예요.

[화면] 강사 얼굴

실습에서는 두 가지를 합니다.
**실습 ①** 법무 에이전트를 새로 만듭니다.
**실습 ②** 슈퍼 호스트 에이전트를 만들어서 HR + 법무를 연결합니다.

---

## M15. 고급도구 — MCP (Model Context Protocol)

**영상 길이:** 약 4분  
**목적:** MCP의 개념과 확장 가능성을 간결하게 소개  

---

[화면] 강사 얼굴 + 하단 자막 "M15. MCP — 외부 도구 확장"

지금까지 에이전트에 연결한 도구들은 대부분 **Microsoft 365 안의 것들**이었습니다.
MCP를 쓰면 **바깥 세계의 도구**도 연결할 수 있습니다.

[자막] MCP = Model Context Protocol

MCP는 **Model Context Protocol**의 약자입니다.
AI 모델이 외부 서비스와 통신하는 **표준 규격**이에요.

[화면] 기존 방식 vs MCP 방식 비교 애니메이션

기존에는 외부 서비스를 연결하려면 **서비스마다 하나씩 커넥터**를 만들어야 했습니다.
10개 서비스면 10개 커넥터.

MCP는 다릅니다.
**MCP 서버 URL 하나**만 넣으면, 그 서버가 제공하는 **도구 수십 개가 한꺼번에** 들어옵니다.

[자막] MCP 서버 URL 하나 → 도구 수십 개 자동 등록

예를 들어, Microsoft Learn MCP 서버를 연결하면
기술 문서 검색 도구가 자동으로 사용 가능해집니다.
GitHub MCP 서버를 연결하면 코드 저장소 관리 도구들이 들어옵니다.

[화면] 강사 얼굴

사용법은 놀라울 정도로 간단합니다.
Copilot Studio의 도구 설정에서 **MCP 서버 URL을 붙여넣기만** 하면 끝.

실습에서 직접 MCP 서버를 연결하고, 새로 생긴 도구가 에이전트에서 동작하는 걸 확인합니다.

MCP는 아직 초기 단계이지만, 앞으로 MCP를 지원하는 외부 서비스가 늘어날수록
에이전트의 활용 범위가 **기하급수적으로 확장**됩니다.

## M16. 고급도구 — 트리거 (이벤트 기반 자동화)

**영상 길이:** 약 5분  
**목적:** 이벤트 트리거의 개념과 Human-in-the-Loop 패턴 설명  

---

[화면] 강사 얼굴 + 하단 자막 "M16. 트리거 — 이벤트 기반 자동화"

지금까지 에이전트는 항상 **사용자가 먼저 말을 걸어야** 동작했습니다.
이번에는 **외부 이벤트가 에이전트를 깨우는** 구조를 만듭니다.

[자막] 채팅 트리거 → 사용자가 시작 / 이벤트 트리거 → 시스템이 시작

[화면] 트리거 시나리오 시퀀스 다이어그램

오늘 만들 시나리오입니다.

**① HR 직원이 Forms에 문의를 작성합니다.**
"연차 계산이 맞는지 확인해주세요"

**② Forms 제출이 트리거를 발동합니다.**
에이전트가 잠에서 깨어납니다. 사용자가 말을 걸지 않아도요.

**③ AI가 문의를 분석하고 답변 초안을 작성합니다.**
자동으로 관련 규정을 찾아서 답안을 만듭니다.

**④ 담당 관리자에게 이메일이 갑니다.**
원래 질문 + AI가 작성한 답변 초안이 함께 갑니다.

**⑤ 관리자가 검토하고 최종 발송합니다.**

[화면] Human-in-the-Loop 패턴 설명
[자막] AI = 속도 / 사람 = 판단 / 결과 = 빠르고 정확

여기서 중요한 패턴이 있습니다. **Human-in-the-Loop.**

AI가 초안을 만들지만, **최종 판단은 사람이 합니다.**
AI의 속도와 사람의 판단이 결합되는 겁니다.

이게 왜 중요하냐면,
AI 답변을 직접 보냈다가 잘못되면 문제가 되잖아요.
하지만 AI가 초안을 만들고, 사람이 검토해서 보내면
**빠르면서도 정확한** 운영이 됩니다.

[화면] 에이전트 진화 정리

정리해볼게요. 에이전트가 어떻게 진화했는지.

M3에서 빈 에이전트로 시작했습니다.
M6~M7에서 지침과 지식을 줬습니다.
M9에서 토픽으로 정보를 수집하게 했습니다.
M11에서 기록하게 했습니다.
M12에서 이메일을 보내게 했습니다.
M14에서 다른 에이전트와 협업하게 했습니다.
M15에서 외부 도구까지 연결했습니다.

그리고 지금, M16에서 **사용자가 없어도 스스로 동작하는** 에이전트가 되었습니다.

[화면] 강사 얼굴

채팅봇에서 시작해서, **운영 자동화 시스템**으로 진화한 겁니다.
이게 오늘 하루의 여정입니다.

실습에서는 Forms를 만들고, 트리거를 연결하고, AI 초안 생성 + 이메일 발송까지 테스트합니다.

수고하셨습니다. 오늘 만든 것을 정리해봅시다.

[화면] 완성 체크리스트 (하나씩 체크 애니메이션)

네 가지 구성요소를 비유로 정리합니다.

- 지식 문서를 우리 회사 실제 문서로 교체

- 엑셀 기록 데이터 분석 (TOP 질문, 패턴 파악)

**다음 단계 (⭐⭐~⭐⭐⭐)**

- 다른 부서용 전문가 에이전트 추가
- MCP로 더 많은 외부 도구 연결

[화면] 트러블슈팅 요약 (8가지)

혹시 문제가 생기면 이 체크리스트를 참고하세요.

1. 답변이 이상하다 → 지식 문서 추가
2. 범위를 벗어난다 → 지침의 범위 명확화
3. 지어낸다 → "모를 때 행동" 지침 추가
4. 토픽이 실행 안 된다 → Description 구체화
5. Copilot에 안 보인다 → 1~3분 대기 + 새로고침
6. Excel 기록 실패 → 테이블 형식 확인
7. Flow 안 돌아간다 → Power Automate 연결 상태 확인
8. 멀티에이전트 라우팅 오류 → 에이전트별 Description 정밀화
